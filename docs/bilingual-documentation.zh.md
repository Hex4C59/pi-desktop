## 1. 目的

本指南定义 pi-desktop 如何维护英文原文和中文译文，同时避免同一项需求、架构、决定或流程出现两份互相竞争的定义。

目标是：

1. 清楚表明哪份文本具有权威性；
2. 让读者在每对文档的相同位置切换语言；
3. 让翻译质量和新鲜度可见；
4. 防止翻译工作静默改变技术含义；
5. 让文档演进过程中的同步工作可评审。

## 2. 核心规则

- 英文是权威原文语言。
- 英文原文保留普通 `.md` 文件名，例如 `runtime-orchestration.md`。
- 中文译文使用相同基础名称并添加 `.zh.md`，例如 `runtime-orchestration.zh.md`。
- 两份文件位于同一目录。
- 中文译文是英文原文的本地化表达，不是第二份权威来源。
- 中英文发生冲突时，以英文原文为准。
- 译文可以改善中文可读性，但不得增加、删除、减弱、加强或重新解释需求和决定。
- 原文错误必须先在英文中修正，再同步中文；仅存在于译文中的错误可以只修改中文文件。

语言权威性与文档权威性和状态相互独立。例如，一份英文 `Draft` 虽然对中文译文具有语言权威性，但仍然不是最终文档。

## 3. 文件配对和语言切换栏

示例：

```text
README.md
README.zh.md

docs/product-requirements.md
docs/product-requirements.zh.md

docs/archive/modules/shared-contracts.md
docs/archive/modules/shared-contracts.zh.md
```

每份成对文档必须在一级标题之后、元数据或正文之前放置语言切换栏。

英文原文：

```markdown
# Document Title

English | [中文](document.zh.md)
```

中文译文：

```markdown
# 文档标题

[English](document.md) | 中文
```

顺序始终是 `English | 中文`。当前语言显示为普通文本，另一种语言使用相对链接。不要使用旗帜图标；存在配对页面时，不要把读者重定向到通用语言索引。

尚无中文译文的英文文档不需要放置无法使用的切换栏。索引可以明确标记中文翻译缺失，但不得链接到占位页面。

## 4. 元数据

英文原文定义文档类型、文档状态、权威范围、适用范围、取代关系和文档关系。中文译文用中文镜像这些事实，不得为自己设置不同的文档状态。

中文译文还必须声明：

- 翻译状态；
- 权威英文原文；
- 存在稳定 Git 版本时的原文版本；
- 最近同步日期。

推荐的中文元数据：

```markdown
- 类型：Architecture
- 状态：Accepted
- 翻译状态：Human Reviewed
- 权威原文：[document.md](document.md)
- 原文版本：`<Git commit>`
- 最近同步：2026-09-18
```

仓库尚无稳定的原文 commit 时，原文版本使用 `Uncommitted baseline`。文档对完成提交后，应尽快替换为 Git commit；不得把未提交基线当成长期同步证据。

英文原文不需要翻译元数据。

## 5. 翻译状态

只使用以下翻译状态：

- `Machine Draft`：由机器生成或经过大幅机器重写，尚未由人工逐行核对；
- `Human Reviewed`：人工已经对照完整英文原文检查准确性和完整性；
- `Technically Verified`：已经完成人工复核，并由具备相关技术或产品领域能力的维护者进一步确认；
- `Stale`：英文原文在记录的版本之后发生变化，译文尚未同步。

翻译状态独立于 `Draft`、`Proposed`、`Accepted`、`Superseded` 和 `Archived` 等文档状态。

不能仅因为模型进行了第二遍检查或反向翻译，就把译文标记为 `Human Reviewed`。评审者可以使用自动化辅助，但该状态表示有人承担评审责任。

## 6. 必须覆盖的范围和优先级

以下文档必须进行双语维护：

- 根目录 README 和文档索引；
- 面向贡献者的 Accepted 需求和决定；
- 当前架构与安全边界文档；
- 构建、测试、打包或发布应用所需的贡献流程。

Draft 可以先用英文起草，在结构稳定后再翻译。模块设计和参考文档根据贡献者需求和实现优先级安排翻译。

讨论日志、归档、已被取代的文档、原始调研记录和生成的参考输出默认不要求全文翻译。它们的索引应说明可用语言。可以只翻译摘要而不翻译完整历史，但不得把摘要描述成完整译文。

## 7. 翻译工作流

创建新的文档对时：

1. 编写或更新完整英文原文；
2. 确认类型、状态、权威范围和关联关系；
3. 使用当前项目术语表和完整原文上下文进行翻译；
4. 保持代码、标识符、命令、路径、URL、事件名和规范性强度不变；
5. 运行结构和链接检查；
6. 对照英文原文评审中文译文；
7. 记录翻译状态、原文版本和同步日期；
8. 在同一次变更中更新索引和配对链接。

更新已有文档对时：

1. 先修改英文原文；
2. 评审原文差异，不为局部变化重新生成整篇中文文档；
3. 将对应变化应用到中文；
4. 检查相邻段落的术语和逻辑连续性；
5. 更新同步元数据；
6. 无法在同一次变更中完成同步时，将译文标记为 `Stale`。

不得为了很小的原文变化重新生成整篇文档，从而覆盖已经人工评审的中文表述。

## 8. 质量要求

评审必须优先保证语义忠实，而不是逐字对应或语言润色。

每次译文变更都必须检查：

- 漏译和原文没有依据的增译；
- 否定、条件、例外、范围、所有权或生命周期发生变化；
- `must`、`must not`、`should`、`may` 及同等规范性措辞的强度变化；
- 混淆已实现、已接受、提议、计划和不支持的行为；
- 数字、版本、限制、路径、命令、标识符或链接被改变；
- 项目术语不一致；
- 对安全、凭据、信任、IPC、持久化或恢复表述作出不安全的改变；
- 标题、列表、表格、代码块和交叉引用不完整。

README、Accepted 需求、ADR、安全文档、IPC contract、持久化格式以及构建或发布说明至少必须达到 `Human Reviewed`。安全边界、公共 contract 和难以逆转的决定，其中文译文应达到 `Technically Verified`，才可视为可靠的实现依据。

机器初译必须显示其状态，且不得成为安全敏感或难以逆转工作所依赖的唯一文本。

## 9. 术语

项目在 [`reference/glossary.md`](reference/glossary.md)（[中文](reference/glossary.zh.md)）维护统一的英中术语表。评审者必须保持现有文档对中的译法一致；有争议的术语应明确标记，而不是静默引入新译法。

术语表至少覆盖：

- desktop host、renderer、runtime、session、task、agent 和 sub-agent；
- steering message、follow-up message、compaction 和 thinking level；
- project trust、credential、tool call、adapter、worktree 和 lifecycle；
- abort、cancellation、retry、recovery、persistence 和 authoritative source；
- `must`、`should` 和 `may` 等规范性用语。

代码标识符和上游 API 名称保持不变，除非周围正文明确解释对应的中文术语。

## 10. 链接和索引

- 配对文档使用相对路径直接互链。
- 中文正文中，如果目标存在当前有效的中文译文，应链接到中文目标；否则链接到英文原文，并在可能令读者意外时说明目标语言。
- 英文原文通常链接到英文目标。
- 重命名或移动任一文件时，必须更新两个语言切换栏、索引、入站链接和同步元数据。
- 文档索引必须说明英文原文具有权威性，不得把过期译文列为当前有效译文。

## 11. 自动化

在仓库根目录运行 `npm run docs:i18n:check`（见 `package.json`）。该检查验证可机械判断的约束：

- 每个 `.zh.md` 文件存在对应的英文 `.md` 原文；
- 配对切换栏存在、双向链接且顺序正确；
- 必需的翻译元数据存在；
- 记录的原文版本存在，以及原文是否在此后变化；
- 相对链接有效；
- 围栏代码块、代码块语言、路径、命令和受保护标识符没有意外变化；
- 必须配对的文档存在中文译文；
- 过期译文在索引或 CI 输出中可见。

段落或标题数量等结构差异可以产生警告，不应无条件失败，因为准确翻译有时需要调整句子结构。自动检查辅助评审，但不能证明翻译质量。

## 12. 现有中文文档迁移

当前仓库的大多数文档使用普通 `.md` 文件名，但内容是中文。不能仅因为本指南被接受，就将它们视为以英文为权威的文档。

迁移应按文档对逐步、原子化进行：

1. 选择一份当前中文文档；
2. 将其内容保留为 `<name>.zh.md`；
3. 创建并评审英文 `<name>.md` 原文；
4. 增加双向语言切换栏和翻译元数据；
5. 更新所有受影响链接和索引；
6. 确认英文版忠实表达此前已经接受的含义；
7. 只有完成以上步骤后，才宣布英文文件是该文档对的权威原文。

文档对完成迁移前，现有文档继续保持当前权威性和语言。不要在普通 `.md` 中留下英文占位内容，不要在翻译中静默降低已接受内容的状态，也不要在缺少经过评审的英文替代文件时批量重命名整个仓库。

除非项目需要另有要求，按以下顺序迁移：

1. `README.md` 和 `docs/README.md`；
2. 文档与贡献指南；
3. Accepted 决定、需求、架构和安全文档；
4. 活跃模块设计和参考资料；
5. 只有存在明确读者需求时才迁移低优先级历史材料。

## 13. 变更评审清单

合并双语文档变更前，确认：

- 对已迁移的文档对，英文原文是唯一语义权威来源；
- 文档状态和翻译状态没有混用；
- 两个语言切换栏都指向对应页面；
- 中文元数据指向正确的原文和版本；
- 所有原文变化均已体现在中文中，否则译文已经标记为 `Stale`；
- 规范性强度、实现状态、安全边界和技术标识符保持不变；
- 相关索引、讨论链接和关联文档已更新；
- 未引入秘密、凭据、敏感路径或不受支持的实现声明。
