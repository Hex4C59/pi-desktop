## 2026-09-18 — 选择双语文档模型

### 问题

仓库需要一种可维护的方式来同时发布英文和中文文档，同时不损失翻译质量，也不产生相互冲突的权威来源。

### 调研和考虑的选项

讨论审视了常见的开源方案：

- 分开的 README 文件；
- 同目录下相互配对的语言文件；
- 镜像 locale 目录；
- 面向独立翻译社区的单独仓库。

同目录配对文件被认为最适合仓库当前规模。在项目尚无文档站点或独立翻译社区时，镜像 locale 目录或独立仓库会增加工作流和同步成本。逐段混合英文和中文的单文件方案被否决，因为它不利于浏览、链接、搜索和维护。

### 用户决定

用户确认：

- 配对的英文和中文页面放在同一目录；
- 英文保留普通的 `<name>.md` 文件名；
- 中文使用 `<name>.zh.md`；
- 英文是权威原文；
- 语言切换器直接位于文档标题下方；
- 切换器顺序为 `English | 中文`；
- 当前语言使用纯文本，另一种语言链接到配对页面。

### 翻译质量顾虑

用户明确提出对翻译质量不佳的担忧。提出的应对方案组合了：

- 唯一的权威源语言；
- 将翻译状态与文档状态分开；
- 重要文档经过人工评审；
- 安全和 contract 材料经过技术验证；
- 英中术语表；
- 原文版本跟踪和可见的过期状态；
- 自动化结构、链接和漂移检查；
- 翻译原文差异，而不是重新生成整份已评审文档。

### 结果

已接受的政策记录在[双语文档维护指南](../bilingual-documentation.zh.md)中。该指南还增加了渐进迁移规则，因为现有普通 `.md` 文件以中文为主：在每一组完整的英文/中文配对被原子地创建并评审之前，它们保留当前权威性。

### 延后工作

本次讨论没有创建：

- 现有中文文档经过评审的英文翻译；
- 优先级指引之外的全仓库迁移计划。

这些是受指南约束的实现任务，而不是尚未解决的政策问题。

项目术语表与 `docs:i18n:check` 已于 2026-09-19 落地；见 [`reference/glossary.md`](../reference/glossary.md) 与 `npm run docs:i18n:check`。
