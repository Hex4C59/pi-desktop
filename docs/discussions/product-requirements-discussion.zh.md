## 2026-09-18 — 讨论目标与材料范围

### 问题

用户希望在阅读 Electron 架构、模块结构和全部模块设计后，通过讨论形成一份需求文档，而不是直接从技术架构推导产品结论。

### 初始材料

现有材料已经较完整地定义：

- Electron Main、Preload、Renderer 和 pi SDK 边界；
- 单活动 runtime、generation 和 sequence；
- workspace、session、agent command 和 model 协调模块；
- 项目信任、凭据、附件和 extension UI；
- 首版 UI 状态和安全要求。

材料主要回答“如何实现”，但没有完整回答“用户为什么需要、首版具体承诺什么、失败后怎样恢复”。

### 代理分析

代理先将 34 份模块设计转译为用户能力、端到端流程、安全要求、错误恢复和待决策项，并指出产品需求不应直接复制 generation、sequence、IPC owner 等实现细节。

### 影响

决定通过逐项讨论确认产品行为，再形成独立的 `product-requirements.md`。

## 2026-09-18 — 产品定位与首版成功标准

### 问题

首版应是一个聚焦的 pi 图形客户端，还是完整替代 pi TUI？

### 代理建议

首版应服务 Linux 开发者，完成“打开项目—处理项目资源—创建或恢复会话—选择模型—与 Agent 对话—查看工具活动—中止或继续—恢复会话”的完整日常闭环，但不追求复制 pi TUI 的全部能力。

### 用户决定

用户确认该定位符合预期。

### 影响

需求文档将“端到端核心工作流可用”作为成功标准，而不是以功能数量或 TUI 完整替代为目标。

## 2026-09-18 — “窗口”和“活动工作区”概念澄清

### 问题

在决定单窗口或多窗口之前，用户要求解释窗口、工作区和活动工作区的含义。

### 概念澄清

讨论区分了：

- 窗口：一个独立的桌面应用窗口；
- 工作区：本地项目目录及其 pi、Git、资源和 runtime 上下文；
- 活动工作区：当前真正连接 runtime 并接收命令的工作区；
- 会话：同一工作区内的一段独立 Agent 对话和上下文。

最初架构建议是单实例、单主窗口、单活动工作区和单活动会话。

### 用户进一步问题

用户没有立即接受该模型，而是要求先对照 ChatGPT Desktop 的实际产品形态。

### 意义

这次澄清避免了把“单实例”“单窗口”“只记住一个项目”和“只能运行一个 Agent”误认为同一件事。

## 2026-09-18 — 对照 ChatGPT Desktop 与 Codex

### 问题

ChatGPT Desktop 属于单活动上下文、多窗口还是单窗口多并行任务？

### 代理调研和分析

讨论得到的区分是：

- 普通 ChatGPT 的 Project/Chat 使用方式接近单窗口中切换当前上下文；
- Companion Window 是轻量辅助窗口，不等于每窗口独立本地 runtime；
- Codex 能力更接近一个应用管理多个并行 Agent 任务。

### 用户决定

用户明确提出：

> 首版就需要支持多个 Agent 后台并行运行，并允许用户在项目或任务之间切换，而不中止之前的任务。

随后确认并行范围包括跨项目和同一项目的不同会话。

### 取代关系

该决定取代了现有架构中的单活动 runtime、切换 session 即 replacement，以及 Renderer 只维护一份当前 conversation 的核心假设。

### 影响

后续需求引入：

- 多项目、多顶层任务；
- 后台任务状态；
- task/runtime registry；
- 多任务事件路由；
- 并发调度；
- 项目树中的状态聚合。

## 2026-09-18 — 同一项目的并行写入隔离

### 问题

同一项目中的多个 Agent 如果共享目录，可能同时修改相同文件、干扰测试和污染 Git 状态。需要决定如何隔离。

### 考虑的选项

- 共享原始目录并警告冲突；
- 自动复制项目目录；
- 为每个任务创建独立 Git worktree；
- 非 Git 项目禁止第二个并行任务。

### 用户决定

- 不同项目可以直接并行；
- 同一 Git 项目的并行写任务默认使用独立 worktree；
- 非 Git 项目、Git 不可用或 worktree 创建失败时，禁止第二个并行 Agent；
- 不静默退化为共享目录，也不自动复制目录。

后续讨论进一步确认：所有 Git 顶层写任务，包括当前唯一任务，也使用独立 worktree，使执行、审查和应用流程一致。

### 重要修正

讨论后续识别到 worktree 只是工作流隔离，不是权限沙箱。pi、shell、extension 和项目程序仍可能通过绝对路径或其他方式访问用户可写位置。

### 影响

需求文档不得承诺 Agent 在技术上绝不写出 worktree，只能承诺 pi-desktop 把默认 cwd 和成果应用流程绑定到 worktree，并明确非沙箱边界。

## 2026-09-18 — 任务成果的审查和应用

### 问题

独立 worktree 中完成的变更怎样回到用户的目标工作区？

### 考虑的选项

- 只显示 worktree 路径，由外部 Git 工具处理；
- 应用内查看 diff 并应用；
- 任务完成后自动提交和合并；
- 按整项、文件或 hunk 应用；
- 在应用内解决冲突，或冲突时停止。

### 用户决定

- 首版在应用内查看文件列表和完整 diff；
- 只支持整项任务一次性应用，不支持按文件或 hunk；
- 目标工作区脏或应用有冲突时停止并保留 worktree；
- 不在目标工作区留下半应用或冲突标记；
- 应用成功后作为未提交修改出现；
- 不自动提交或合并；
- 未应用成果可以在二次确认后永久丢弃。

### 后续安全分析

“原子应用”最初表述过强。后续增加了：

- base commit；
- `resultRevision`；
- 审查后变化使结果失效；
- 预应用检查；
- apply journal；
- 对二进制、符号链接、submodule、LFS 等能力边界的实现期定义。

### 未解决问题

具体 Git 应用算法和异常恢复实现仍待架构与技术 spike。

## 2026-09-18 — 顶层任务与子 Agent

### 问题

同一会话是否允许多个主 Agent 同时运行，以及主 Agent 内部并行工作如何呈现？

### 用户决定

- 每个顶层会话同一时间最多一个主 Agent；
- 主 Agent 可以启动并行子 Agent；
- 并行顶层工作通过多个任务或会话实现；
- 子 Agent 以详细树展示任务说明、状态、输出、工具、模型、用量和父子关系；
- 用户可以单独中止子 Agent，但不能直接向它发送消息；
- 中止主任务时级联取消子 Agent；
- 阻塞完成的子 Agent 全部结束、失败或取消后，主任务才能最终完成。

### 后续能力核查

后续审查指出，当前 pi SDK 文档不能直接假定存在完整的一等子 Agent API。需要通过上游稳定公共 API 或 pi-desktop 自有的、经过兼容保护的 custom tool/runtime 协议完成 spike。

### 未解决问题

- 子 Agent 的具体公共 API 或自有协议；
- 嵌套深度；
- 子 Agent session/runtime 所有权；
- extension UI 和用量如何路由到父任务。

## 2026-09-18 — 关闭窗口与重启恢复

### 问题

“后台运行”是否表示关闭主窗口后仍继续执行？

### 用户决定

- 后台运行只表示在应用内切换到其他项目或任务后继续；
- 关闭窗口且仍有运行任务时显示确认；
- 用户确认退出后中止所有主任务并级联取消子 Agent；
- 首版不驻留托盘；
- session、任务记录、follow-up 和未应用 worktree 保留；
- 重启后原运行任务标记为 interrupted，不自动继续；
- 用户可恢复原会话，在原 worktree 中补充“继续”指令。

### 重要澄清

恢复原会话不等于从被中断的命令执行点继续。旧工具和子 Agent应标记为 interrupted，新一轮重新检查文件、Git 和模型状态。

### 后续持久化修正

要恢复尚未执行的 follow-up 内容，就必须在 Main 控制、权限受限的专用任务状态存储中持久化用户消息。不能同时声称“恢复队列内容”和“只保存非秘密 metadata”。

## 2026-09-18 — 项目 `.pi` 资源和“不加载但继续打开”

### 用户疑问

用户在 Codex Desktop 中没有明显遇到“不信任项目”选项，因此追问为什么 pi-desktop 需要该选择，以及 `.pi` 资源的作用。

### 概念澄清

讨论说明 `.pi` 可能包含：

- 项目设置；
- 可执行 extension；
- skill；
- prompt template；
- system prompt；
- theme；
- 项目 package。

项目信任控制是否加载这些项目资源，不控制 Agent 是否有用户权限，也不是沙箱。Codex 也有项目配置可信性概念，但同时还有不同的 OS sandbox 和 approval 模型，因此用户体验未必相同。

### 考虑的选项

- 不信任时完全拒绝打开；
- 以所谓只读模式打开；
- 不加载项目资源但继续打开。

### 用户决定

选择“不加载项目资源但继续打开”。

具体确认：

- “仅本次加载”对当前应用进程中的该项目及其任务有效；
- “不加载项目资源”持久记住；
- 提供“更改项目资源设置”入口；
- 文案使用“加载项目资源/不加载项目资源”，而不是只显示抽象的“信任/不信任”；
- 明确提示这不是沙箱。

### 后续架构问题

pi trust store 按规范化路径工作，而 task worktree 是内部临时路径。产品信任范围应绑定稳定 `projectId`，持久决定写原项目路径，临时决定留在 Main project registry，不能为每个 worktree 留下独立 trust 记录。

## 2026-09-18 — Extension UI 完整支持

### 问题

加载项目 extension 后，如果 Desktop 不支持交互，extension 可能永久等待。

### 用户决定

首版完整支持：

- `select`；
- `confirm`；
- `input`；
- `editor`；
- `notify`。

并行环境中请求必须标明项目、顶层任务和子 Agent；后台请求进入 waiting，并能从项目树和桌面通知跳转。中止、崩溃、退出或超时必须解决 pending request。

## 2026-09-18 — 并发上限和调度

### 问题

多个顶层 Agent 和子 Agent可能同时消耗系统资源和 provider 配额，需要决定是否限制并发。

### 用户决定

采用可配置的保守默认值，并分别限制：

- 顶层任务；
- 单任务子 Agent；
- 全局 Agent总数。

默认值确认为：

- 顶层任务 3；
- 每任务子 Agent 3；
- 全局总数 6。

超限后排队，不直接失败。

### 后续死锁修正

如果主 Agent占用全部槽位并同步等待 queued 子 Agent，可能死锁。需求后续增加：

- 主 Agent等待子 Agent时释放模型执行槽；
- 已被父任务依赖的子 Agent优先于新顶层任务；
- 有界等待、取消和饥饿保护。

## 2026-09-18 — 主界面结构与后台状态发现

### 问题

单窗口怎样同时管理多个项目、任务、会话、子 Agent 和待审查成果？

### 用户决定

采用三栏结构：

- 左侧项目/任务树；
- 中央当前会话；
- 右侧任务详情、子 Agent 和变更审查。

用户拒绝单独建立全局待办中心，首版主要依靠项目和任务树中的持久状态标记。等待输入、失败、已中断和待审查必须在树中可见，不能只靠颜色或桌面通知。

## 2026-09-18 — Git 任务起点与原始脏工作区

### 问题

新 worktree 应从默认分支、用户选择的 commit，还是原始工作区当前 `HEAD` 创建？原始工作区有未提交修改时怎么办？

### 用户决定

- 默认基于当前检出的 `HEAD`；
- 创建前显示分支和短 commit ID；
- detached HEAD 可以使用但必须标明；
- 原始工作区有未提交修改时仍允许创建；
- 明确提醒任务看不到未提交修改；
- 不自动 stash、提交或复制这些修改。

后续应用仍要求目标工作区干净，因此持续存在的本地修改会阻止应用成果。

## 2026-09-18 — 任务完成、验证和成果状态

### 问题

Agent 停止生成是否等同于任务成功？测试未运行或失败如何表达？

### 用户决定

分开显示：

1. Agent 执行状态；
2. 验证状态；
3. 成果审查状态。

Agent 完成不等于测试通过，测试失败不自动丢弃变更，测试通过也不自动应用。

### 后续细化

验证记录应绑定 `resultRevision`，包含命令、cwd、退出状态、时间和来源。文件变化后旧测试结果不能继续代表当前成果。

## 2026-09-18 — 模型选择和子 Agent 模型

### 问题

模型配置是全局、任务级，还是每条消息独立？子 Agent 使用什么模型？

### 用户决定

- provider、模型和 thinking level 按消息选择；
- 消息被接受时形成快照；
- 多任务可以使用不同模型；
- 主 Agent可以为子 Agent选择已认证且允许的模型；
- UI 显示子 Agent实际模型，不静默替换。

### 后续上游语义修正

pi SDK 的模型主要是 session 级状态，原生 steer/follow-up 队列不携带独立模型快照。因此需求后续澄清：

- steer 继承当前 run 的配置；
- 需要独立模型的 follow-up 由 Desktop 延迟调度，在下一轮开始前设置；
- 不能仅依靠上游原生队列实现该承诺。

## 2026-09-18 — 用量和费用

### 问题

并行 Agent 是否需要预算阈值和自动暂停？

### 用户决定

首版只展示 token 和费用，不自动暂停：

- 子 Agent单独显示并汇总到顶层任务；
- 项目和应用运行期可聚合；
- 区分实际费用与估算；
- 未知价格显示“费用未知”，不能显示虚假的零。

硬性预算留待后续版本。

## 2026-09-18 — Linux 桌面通知

### 问题

用户查看其他任务时，后台任务的等待输入、失败或完成如何提醒？

### 用户决定

- 等待输入和失败默认通知；
- 普通完成通知默认关闭，可配置开启；
- 当前可见任务不重复通知；
- 点击通知定位正确任务；
- 通知脱敏且去重；
- 项目树是持久状态来源，通知只是辅助。

## 2026-09-18 — 运行中的新消息和中止

### 问题

主 Agent运行时发送新消息，默认应立即 steer 还是加入 follow-up？中止后队列怎么办？

### 用户决定

- 默认作为 follow-up；
- 用户可以显式切换为 steer；
- 中止当前运行时保留 follow-up，但暂停队列；
- 不自动执行下一条；
- 用户随后决定继续、编辑或清空。

调度队列、follow-up 队列和 provider retry 必须清楚区分。

## 2026-09-18 — 通用文件附件

### 问题

现有架构只设计图片，但编码 Agent 用户可能希望附加文本、日志、文档或其他文件。

### 用户决定

- 首版产品入口支持受控通用文件附件；
- 外部附件只用于当前消息；
- 不复制进任务 worktree；
- 不成为后续消息默认可访问文件；
- Renderer 只持有 metadata 和短生命周期 token。

### 后续能力收窄

上游 prompt 原生主要支持文本和图片。后续审查要求实现规格按真实转换能力处理：

- 图片映射为上游图片内容；
- 文本按编码和大小限制注入当前消息；
- PDF、办公文档、压缩包等二进制类型在安全解析或引用方案确定前明确拒绝；
- 不能只展示可选择入口就假装模型可以读取。

## 2026-09-18 — 需求文档起草与交叉审查

### 过程

用户选择直接起草完整需求文档。初稿形成后，对照架构、模块和上游 pi 能力进行了交叉审查。

### 发现的主要风险

- worktree 被误写成比实际更强的权限隔离；
- 子 Agent 能力缺少稳定上游集成依据；
- follow-up 重启恢复与“不保存 prompt”矛盾；
- 按消息模型与 session 级模型语义冲突；
- apply 的绝对原子承诺缺少算法和恢复依据；
- 同进程 runtime 不能保证单任务崩溃后主窗口仍存活；
- trust 决定不能直接按临时 worktree 路径持久化；
- task、session、worktree 和成果版本需要独立领域实体；
- 多级调度存在父任务等待子 Agent的潜在死锁。

### 修正

需求文档随后增加或收窄：

- worktree 非沙箱说明；
- 子 Agent spike 前置条件；
- follow-up 受控持久化；
- `resultRevision` 和 apply journal；
- 调度防死锁规则；
- 可捕获 runtime 异常与 main process 崩溃的区别；
- task registry 和新增资源 owner 清单；
- 更完整的异常、失步、安全和恢复验收场景。

### 当前结果
