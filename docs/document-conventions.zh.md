## 1. 目的

本规范用于让需求、架构、模块设计、决策、讨论过程、操作指南和历史材料在数量增长后仍然容易查找、判断和维护。

文档体系必须帮助读者回答：

1. 这是什么类型的文档？
2. 它当前是否有效？
3. 它对什么内容具有权威性？
4. 它与哪些需求、架构、决策和讨论记录有关？
5. 如果文档冲突，应以什么为准？
6. 这个结论是怎样形成和修正的？

## 2. 基本原则

- 目录表达文档类型，文档头部表达状态、适用范围和关系。
- 当前有效结论与形成过程分开保存。
- 一个概念只保留一个权威定义，其他文档使用摘要和链接。
- 讨论日志保存真实思考过程，不根据最终结论反向美化历史。
- 被取代的观点和文档应明确标记，不静默删除。
- 不使用 `final`、`latest`、`new`、`v2` 等文件名表达状态。
- 文档状态由元数据和 Git 历史表达。
- 新建文档前先搜索是否已有相同权威范围的文档。
- 文档不得包含凭据、秘密、完整敏感路径或不适合进入仓库的原始聊天内容。
- 双语文档使用同目录逐页配对；英文 `<name>.md` 是完成迁移后文档对的权威原文，中文使用 `<name>.zh.md`。翻译状态、同步和迁移规则以[双语文档维护指南](bilingual-documentation.zh.md)为准。

## 3. 目录分类

目标结构如下：

```text
docs/
├── README.md
├── requirements/
├── architecture/
├── modules/
├── decisions/
├── discussions/
├── guides/
├── reference/
├── assets/
└── archive/
```

各目录职责：

- `requirements/`：产品目标、用户行为、范围和验收标准；
- `architecture/`：系统结构、进程模型、数据流、安全边界和架构评审；
- `modules/`：单个模块的职责、所有权、依赖、禁止事项和测试边界；
- `decisions/`：长期有影响的重要决策记录，即 ADR；
- `discussions/`：按时间整理的需求、架构和设计讨论过程；
- `guides/`：开发、测试、提交、构建、打包和发布等操作规范；
- `reference/`：术语、状态模型、协议和其他查询型资料；
- `assets/`：图、图片和文档使用的静态资源；
- `archive/`：已失效但仍有历史价值的完整文档。

仓库当前仍在初始化阶段。不要仅为目录整齐而一次性移动全部现有文件。现有文档在下一次实质性修订时逐步迁移，并同时修复全部链接和索引。

## 4. 文档类型

每份文档应使用以下一种主要类型：

- `Requirement`：定义用户需求、产品行为、范围和验收标准；
- `Architecture`：定义系统结构、边界、所有权和关键技术约束；
- `Module Design`：定义单个模块的职责、依赖和测试重点；
- `Decision`：记录一个重要决定的背景、选项、结果和后果；
- `Discussion`：按时间保存形成需求或设计的讨论过程；
- `Guide`：说明应如何执行一个流程；
- `Reference`：提供稳定的查询信息；
- `Archive`：保存已失效材料。

一份文档只有一个主要类型。确实包含多种内容时，应拆分或明确唯一的权威范围。

## 5. 文档状态

只使用以下状态：

- `Draft`：正在形成，可能大幅修改；
- `Proposed`：内容基本完成，等待确认；
- `Accepted`：已经确认，是当前有效依据；
- `Superseded`：已被另一份文档或决定取代；
- `Archived`：不再参与当前设计，仅保留历史参考。

如需表达评审进度，可增加独立的“评审”字段，不创建含义相近的新状态。

## 6. 元数据

新建或实质性修订文档时，在标题后提供适用的元数据。推荐格式：

```markdown
# 文档标题

- 类型：Requirement
- 状态：Draft
- 创建日期：2026-09-18
- 最近评审：2026-09-18
- 适用阶段：首个可用版本
- 领域：Task、Runtime、Scheduler
- 权威范围：用户可见的任务调度行为
- 取代：无
- 被取代：无
- 相关文档：...
- 讨论记录：...
- 相关决策：...
```

字段按需要使用，但以下内容必须能够判断：

- 类型；
- 状态；
- 适用范围或阶段；
- 权威范围；
- 相关当前文档；
- 对应讨论日志（存在时）；
- 取代关系（存在时）。

不要维护无法长期保持准确的装饰性字段。单人或尚未明确责任人的阶段不强制填写 Owner。

## 7. 权威性与冲突处理

不同文档对不同问题具有权威性：

1. 根目录 `AGENTS.md`（内核）与 `docs/guides/agent/` 下 playbook 共同定义仓库开发、安全和代理行为约束；内核加载地图说明各 playbook 的适用时机；
2. Accepted Requirement 定义用户可见行为、产品范围和验收标准；
3. Accepted Decision 定义其明确覆盖的重要决定；
4. 当前 Architecture 定义系统结构、资源所有权和技术边界；
5. Module Design 定义模块内部职责和依赖；
6. Guide 和 Reference 定义具体流程或查询信息；
7. Discussion 只提供历史背景，不作为当前实现依据；
8. Superseded 和 Archive 文档不参与当前实现决策。

发现冲突时：

- 不通过猜测静默选择；
- 在 `docs/README.md` 的“已知冲突”中记录；
- 明确哪个领域由哪份文档权威定义；
- 修订受影响文档或创建待决策项；
- 在冲突解决前，不把互相矛盾的内容都描述为已接受。

## 8. 命名和目录深度

- 文件名使用小写 kebab-case，例如 `runtime-orchestration.md`；
- ADR 使用四位编号，例如 `0001-use-electron.md`；
- discussion 文件使用对应主题名，例如 `product-requirements-discussion.md`；
- 目录通常不超过 `docs/<type>/<file>` 或 `docs/<type>/<topic>/<file>`；
- 不在文件名中使用日期表示版本；日期只用于 discussion 时间线或确有时间分片需求的日志；
- 不使用“最终版”“最新版”“新版本”等名称。

## 9. 链接和索引

- `docs/README.md` 是文档体系总入口；
- 新建、移动、取代或归档重要文档时同步更新总索引；
- 最终文档与对应 discussion 应双向链接；
- ADR 应链接到受影响的需求或架构文档；
- 使用仓库相对链接，不提交机器绝对路径；
- 移动文件时搜索并修复所有相对链接；
- 不复制大段权威定义来避免链接，应提供简短上下文后链接原文。

## 10. 讨论日志

### 10.1 何时记录

当任务经过实质性讨论并创建或显著修改以下内容时，应创建或更新 discussion：

- 产品需求；
- 系统或模块架构；
- 安全和信任模型；
- 持久化、恢复或协议；
- 构建、发布或兼容策略；
- 难以逆转或存在多个有效选项的重要设计。

简单拼写修正、机械格式调整、显然的局部修复和没有设计决策的文档编辑不需要讨论日志。

### 10.2 组织方式

- 默认每个重要最终文档对应一份持续追加的 discussion；
- discussion 放在 `docs/discussions/`；
- 多次聊天围绕同一文档时追加到同一文件；
- 只有文件过长、主题形成独立文档或维护明显困难时才拆分；
- 不默认每次聊天新建一个文件；
- 不逐字复制完整聊天。

### 10.3 时间线条目

每个条目至少包含适用部分：

```markdown
## 2026-09-18 — 主题

### 问题

当时需要回答什么？

### 初始假设

讨论开始时认为是什么？

### 用户思考

用户表达了什么目标、疑问、顾虑或偏好？

### 代理分析

代理提供了哪些解释、选项或建议？

### 考虑的选项

- 选项及其优缺点；
- 被拒绝选项的原因。

### 决定

用户明确确认了什么？

### 影响

最终文档、架构或后续工作发生了什么变化？

### 取代关系

哪些旧假设被取代？

### 未解决问题

还有什么没有决定？
```

不要求每个条目机械地包含所有小节，只保留真实存在的信息。

### 10.4 忠实性要求

- 明确区分用户观点、代理建议和最终确认；
- 不把代理建议写成用户已经决定；
- 不根据最终结果编造用户当时没有表达的理由；
- 不删除早期错误、犹豫或被拒绝方案；
- 后续改变决定时追加新条目，并明确标记旧决定被取代；
- 无法确认归属时写“讨论中提出”，不要猜测；
- 保留关键概念澄清，例如用户为何改变理解；
- 删除闲聊、重复确认和不影响思考过程的操作细节；
- 对原始聊天中可能存在的秘密和敏感路径进行脱敏；
- 最终文档始终是当前行为的权威来源，discussion 不是实现规范。

## 11. ADR

只有符合以下至少一项时才创建 ADR：

- 改变系统、进程或模块边界；
- 改变安全、信任或权限模型；
- 改变持久化格式或公共 contract；
- 很难或代价很高地逆转；
- 拒绝了多个有竞争力的方案；
- 新成员以后很可能询问“为什么这样做”。

ADR 至少包含：

- Context；
- Options considered；
- Decision；
- Consequences；
- Status；
- Date；
- Related documents。

不要为普通 UI 文案、组件命名或局部实现细节创建 ADR。

## 12. 归档和取代

- 内容被新文档取代时，先将状态改为 `Superseded` 并链接取代者；
- 文档整体不再参与当前设计时可以移动到 `archive/`；
- discussion 中的旧条目不移动、不重写，只追加取代说明；
- 归档文件仍需保留来源、原状态和取代链接；
- 不以删除历史的方式制造表面一致性。

## 13. AI 维护流程

创建、移动、拆分、归档或实质性修改项目文档时：

1. 阅读本规范和 `docs/README.md`；
2. 搜索已有文档，确认不会建立重复权威来源；
3. 确定类型、状态和权威范围；
4. 选择稳定文件名和目录；
5. 更新对应最终文档；
6. 若存在实质性讨论，追加对应 discussion 时间线；
7. 若形成长期重要决定，评估是否需要 ADR；
8. 更新总索引和相关双向链接；
9. 记录已知冲突和取代关系；
10. 检查所有相对链接、格式和敏感信息；
11. 不把计划功能写成已实现功能；
12. 在结果中说明新增、更新和仍待决定的文档。

## 14. 当前迁移策略

当前文档保留原路径。后续按以下方式渐进迁移：

- 实质性修订需求文档时迁入 `requirements/`；
- 实质性修订系统架构文档时迁入 `architecture/`；
- 模块文档继续位于 `modules/`；
- Git 提交规范后续可迁入 `guides/`；
- 每次移动都必须同步更新索引和全部链接；
- 不进行与当前任务无关的批量路径重构。
