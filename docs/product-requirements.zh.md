## 1. 产品概述

pi-desktop 是面向 Linux 开发者的 pi 图形桌面客户端。它在复用 pi agent、模型、工具、会话、资源和扩展机制的前提下，提供适合日常高频开发工作的多任务桌面界面。

首版必须让用户完成以下端到端闭环：

1. 打开本地项目，并明确决定是否加载项目提供的 pi 资源；
2. 创建或恢复顶层任务与会话；
3. 在隔离的 Git worktree 中运行一个或多个 Agent 任务；
4. 在不同项目和任务之间切换，而不中止后台运行；
5. 查看流式回答、thinking、工具执行和子 Agent 活动；
6. 处理 extension 发起的交互、失败和等待状态；
7. 审查 Agent 产生的完整代码变更；
8. 将整项变更安全应用回目标工作区，或明确丢弃；
9. 在应用重启后恢复任务记录、会话和未处理 worktree 成果。

首版不以完整替代 pi TUI、IDE 或通用 Git 客户端为目标。

## 2. 产品目标

### 2.1 核心目标

- 提供单窗口、多项目、多顶层任务的 Agent 工作台；
- 支持跨项目、跨会话的多个 Agent 后台并行运行；
- 使用独立 Git worktree 隔离同一项目中的写任务；
- 让主 Agent 启动的子 Agent 可见、可追踪并可单独中止；
- 保留 pi 的流式消息、工具调用、队列、中止、重试、压缩和树状会话语义；
- 让用户在应用内审查完整 diff，再决定是否应用变更；
- 保持工作目录、运行状态、模型、用量和待处理交互清楚可见；
- 隔离 Renderer 与高权限 runtime，不向界面暴露凭据或通用系统能力；
- 在切换、退出、失步、错误和崩溃后保持任务归属明确且可恢复。

### 2.2 首版成功标准

首版只有在以下条件全部满足时才视为可用：

- 用户可以同时启动至少两个不同项目的顶层任务，并在任务间切换而不影响后台运行；
- 用户可以在同一 Git 项目中创建多个使用独立 worktree 的顶层任务；
- 每个顶层会话同一时间最多运行一个主 Agent，但主 Agent 可以启动多个并行子 Agent；
- 后台任务的等待输入、失败、中断、完成和待审查状态不会被遗漏；
- pi-desktop 将每个 Git 任务的默认工作目录绑定到独立 worktree，且自身不会在用户确认前把任务成果应用到原始 Git 工作区；界面明确说明 worktree 是工作流隔离而不是系统权限沙箱；
- 用户能够查看完整任务 diff，并将全部变更作为未提交修改应用到干净的目标工作区；
- 目标工作区脏或应用存在冲突时，应用安全停止，不留下半应用状态；
- 应用退出不会自动丢弃未应用的 worktree 成果；
- 应用重启后可以恢复任务记录和 worktree，并由用户手动继续已中断任务；
- 凭据、完整 prompt、附件内容和敏感诊断信息不会泄漏到 Renderer 持久化、普通日志或系统通知。

## 3. 目标用户与核心场景

### 3.1 目标用户

- 在 Linux 上进行本地软件开发的用户；
- 已使用或希望使用 pi agent、模型、工具、session、extension、skill 和 prompt 的用户；
- 需要并行推进多个编码任务，并审查每个任务成果的开发者；
- 重视任务隔离、可观察性、键盘效率和变更控制的高频用户。

### 3.2 核心场景

- 在项目 A 中运行实现任务，同时在项目 B 中运行调查任务；
- 在同一 Git 项目中为多个独立任务创建 worktree，并行执行而不相互污染；
- 查看一个主 Agent 内部启动的多个子 Agent及其工具活动；
- 切到其他任务后，让原任务继续运行并在需要输入时提醒用户；
- 任务完成后检查文件列表、完整 diff、测试结果和用量，再整项应用；
- 退出应用后保留未应用成果，下次启动时恢复并继续原会话。

## 4. 核心概念

### 4.1 项目

项目是用户选择的本地工作目录及其 pi、Git 和任务上下文。项目可以包含多个顶层任务。首版项目通常对应一个 Git 仓库；非 Git 目录可以运行单个任务，但不支持同项目并行任务。

### 4.2 原始工作区

原始工作区是用户最初选择的本地项目目录。对于 Git 项目，pi-desktop 将任务 runtime 和内置工具的默认工作目录绑定到独立 worktree；任务成果只有在用户确认应用后，才由 pi-desktop 作为未提交修改写回原始工作区。

Git worktree 是工作流隔离，不是系统权限边界。pi、shell、extension 和项目进程仍以当前用户权限运行，可能通过绝对路径、符号链接或外部程序访问其他用户可写位置。若用户需要“无法写出 worktree”的保证，必须使用容器、VM 或操作系统级沙箱；首版不作此承诺。

### 4.3 顶层任务与会话

顶层任务是用户在项目中创建或恢复的独立工作单元，并绑定一个 pi 会话和一个实际工作目录。每个顶层任务同一时间最多有一个主 Agent 运行。

### 4.4 子 Agent

子 Agent 是主 Agent 为完成当前顶层任务而创建的内部并行执行单元。子 Agent：

- 归属于一个顶层任务；
- 与父任务共享任务 worktree；
- 不成为独立顶层会话；
- 可以并行运行；
- 可以查看并单独中止；
- 不能由用户直接发送消息；
- 其结果由主 Agent 汇总和使用；
- 只有所有阻塞完成的子 Agent 均已完成、失败或取消，主任务才能进入最终完成状态。

### 4.5 任务 worktree

对于 Git 项目，每个顶层写任务都在独立 Git worktree 中执行，包括项目当前唯一运行的任务。worktree 基于任务创建时原始工作区当前检出的 `HEAD`，并记录不可变的 base commit。

### 4.6 当前查看任务与后台任务

当前查看任务是中央会话区域正在显示的任务。后台任务是未显示但仍处于运行、排队、等待输入或其他活动状态的任务。切换当前查看任务不得中止后台任务。

## 5. 首版范围

### 5.1 包含

- Linux 单实例、单主窗口；
- 多项目和多顶层任务导航；
- 跨项目、跨会话并行 Agent；
- Git worktree 创建、保留、检查和安全清理；
- session 创建、恢复、切换、fork 和重命名；
- prompt、steer、follow-up、中止和清空 follow-up 队列；
- 主 Agent 与子 Agent 的详细状态和活动；
- provider、模型、thinking level 和认证；
- 每条消息独立选择模型与 thinking level；
- 文本、Markdown、代码、diff、thinking 和工具活动；
- 受控通用文件附件；
- extension 的 `select`、`confirm`、`input`、`editor` 和 `notify`；
- token 与费用展示；
- 完整任务 diff 审查、整项应用和明确丢弃；
- Linux 桌面通知；
- 应用重启后的任务、会话和 worktree 恢复。

### 5.2 明确不包含

- Windows 和 macOS；
- 多主窗口；
- 应用关闭后驻留系统托盘继续运行；
- 同一顶层会话同时运行多个主 Agent；
- 非 Git 项目中的同项目并行 Agent；
- 自动复制非 Git 项目以实现隔离；
- 自动提交、自动合并或自动创建 Pull Request；
- 按文件或 diff hunk 选择性应用；
- 内置 Git 冲突解决器；
- 自动继续应用退出前正在运行的 Agent；
- 用户直接向子 Agent 发送消息；
- 硬性 token 或费用预算；
- 项目信任的系统沙箱承诺；
- 通用 Renderer 文件系统或 shell 接口；
- 直接解析或改写 pi session JSONL；
- 远程 Agent 服务和多设备同步；
- 自动更新和 Flatpak 权限模型。

## 6. 信息架构

### 6.1 主窗口

首版采用三栏主界面：

```text
项目 / 任务树 | 当前会话 | 任务详情
```

#### 左侧：项目与任务树

按项目分组显示顶层任务。项目节点聚合显示：

- 运行中数量；
- 等待并发槽位数量；
- 等待用户输入数量；
- 失败数量；
- 已中断数量；
- 待审查数量。

任务节点至少显示：

- 任务名称；
- 主执行状态；
- 未读状态；
- 验证状态摘要；
- 成果状态摘要；
- worktree 或分支摘要。

首版不设置独立的全局待办中心。关键待处理状态必须在项目树中持久可见，不能仅依赖瞬时通知。

#### 中央：当前会话

显示当前任务的：

- 用户和 assistant 消息；
- 流式文本与 thinking；
- 工具调用；
- retry、compaction 和错误；
- Composer；
- steer 与 follow-up 入口。

切换中央当前任务只改变显示内容，不改变任何后台任务的运行状态。

#### 右侧：任务详情

根据上下文显示：

- 顶层任务状态；
- 子 Agent 树；
- 工具详情；
- 实际工作目录与 base commit；
- 模型、thinking level 和用量；
- 文件变更与完整 diff；
- 验证结果；
- 应用或丢弃操作。

窄窗口下右侧栏可以收起或变为抽屉，但中央会话和 Composer 必须保持可用。

### 6.2 状态表达

状态不能只通过颜色表达。任务树、会话和详情面板应组合使用文字、图标、计数和 accessible label。

## 7. 项目打开与项目资源

### 7.1 打开项目

用户可以通过系统目录选择器打开项目。应用必须：

1. 规范化和验证真实路径；
2. 检查目录是否存在、可读及是否为 Git 仓库；
3. 检查是否存在需要信任的 pi 项目资源；
4. 完成适用的项目资源决定；
5. 创建项目记录并加载任务列表；
6. 仅在成功后记录最近项目。

取消目录选择不得显示错误或改变当前状态。

### 7.2 项目资源提示

当项目包含需要信任的 pi 资源且没有适用决定时，界面不使用含糊的单纯“信任/不信任”文案，而应说明项目包含可以影响 Agent 行为或执行代码的资源，并提供：

- **加载并记住**：持久允许加载；
- **仅本次加载**：只在当前应用进程生命周期内允许；
- **不加载项目资源**：持久跳过受保护资源，但继续打开项目；
- **取消打开**：不打开项目。

受保护资源包括上游 pi 定义的项目设置、extension、skill、prompt、theme、system prompt、项目 package 和项目 `.agents/skills`。

### 7.3 不加载项目资源

用户选择“不加载项目资源”后：

- 项目仍可打开；
- 用户仍可创建、恢复和运行 Agent 任务；
- 跳过受项目信任保护的资源；
- 项目树和任务详情持续显示“项目资源未加载”；
- 用户可以查看被跳过的资源类型；
- 应用提供“更改项目资源设置”入口；
- 不把此状态描述为只读、安全模式或沙箱；
- 必须明确说明 Agent 仍以当前用户权限读取、修改文件和执行命令。

“不加载项目资源”是持久决定。Desktop 必须通过 pi 公共 API 和 trust store 语义处理，不自行解析或改写 `trust.json`。

### 7.4 仅本次加载

“仅本次加载”在当前 pi Desktop 进程存活期间，对该项目创建或恢复的所有任务及其 worktree 有效：

- 不写入持久信任记录；
- 当前进程中再次打开不重复询问；
- 应用完全退出后失效；
- 下次启动时重新询问。

项目资源决定不能热切换已经运行的 runtime。修改决定只影响之后创建或重建的任务。

产品层的信任作用域绑定稳定 `projectId`，而不是临时 worktree 路径。持久决定仍按 pi 公共 API 写入原始规范化项目路径；“仅本次加载”保存在 Main 进程内的项目级临时 registry；创建 worktree runtime 时显式应用该项目决定，且不得为内部 worktree 路径留下独立持久信任记录。该行为必须先通过固定 pi 版本的公共 API 验证。

## 8. 任务创建与 worktree 隔离

### 8.1 Git 项目

所有可能写入代码的顶层任务都必须使用独立 worktree，即使当前项目只有一个任务。

新任务默认基于原始工作区当前检出的 `HEAD`：

- 创建前显示分支或 detached HEAD 状态；
- 显示短 commit ID；
- 记录 base commit；
- 不自动包含原始工作区的未提交改动。

### 8.2 原始工作区存在未提交修改

用户仍可创建任务，但应用必须：

- 醒目标出原始工作区为脏状态；
- 显示未提交变更文件数量；
- 明确说明任务只基于当前 `HEAD`，看不到未提交修改；
- 不自动 stash、提交、复制或修改用户原始工作区；
- 允许用户继续或取消。

### 8.3 非 Git 项目

非 Git 项目可以直接在原目录运行一个顶层任务，但：

- 同项目存在活动或保留的写任务时，禁止启动第二个并行任务；
- 不自动复制目录；
- 不静默退化为共享目录并行；
- 错误信息应建议等待现有任务结束，或将项目初始化为 Git 仓库。

Git 不可用、worktree 创建失败、权限不足或路径冲突时，同样不得启动需要隔离的新任务。

### 8.4 子 Agent 工作目录

同一顶层任务的子 Agent共享父任务 worktree。界面应说明同任务内部的并行子 Agent可能同时操作相同文件，主 Agent负责协调其工作。

子 Agent 不是当前 pi SDK 文档中可直接假定存在的一等稳定能力。实现前必须通过上游稳定公共 API，或由 pi-desktop 明确定义且经过兼容性保护的 custom tool/runtime 协议完成 spike，验证创建、事件、取消、模型、用量和 extension UI 路由。若固定的 pi 版本不能可靠提供这些语义，首版实现不得静默降级或伪造子 Agent 状态，而应在架构决策阶段阻止进入实现。

## 9. 多 Agent 并发与调度

### 9.1 并发范围

首版允许：

- 不同项目的顶层任务并行；
- 同一 Git 项目的不同顶层任务并行；
- 一个主 Agent 在任务内部启动多个子 Agent。

每个顶层会话同一时间最多运行一个主 Agent。

### 9.2 默认上限

首版默认并发上限为：

- 同时运行的顶层任务：3；
- 每个顶层任务同时运行的子 Agent：3；
- 全局同时执行的主 Agent与子 Agent总数：6。

用户可以在设置中调整这些值。

### 9.3 调度行为

- 超过上限的 Agent进入“等待并发槽位”，而不是失败；
- 设置变更只影响后续调度，不强制中止已运行 Agent；
- 等待用户输入的 Agent不占模型执行槽；
- 主 Agent等待子 Agent结果时释放模型执行槽，但仍保持任务活动状态；
- 等待结束后若槽位已满，则重新进入调度队列；
- 已获父任务依赖的 queued 子 Agent优先于新的顶层任务调度，避免父任务占槽等待导致死锁；
- 调度器必须提供有界等待、取消和饥饿保护；无法为子 Agent建立可调度请求时，创建操作应明确失败，不能无限等待；
- 子 Agent同时受单任务上限和全局上限约束；
- 调度队列、follow-up 队列和 provider retry 必须在状态与文案上明确区分。

## 10. 主 Agent 与子 Agent

### 10.1 子 Agent 可见性

任务详情提供可展开的子 Agent 树，至少显示：

- 名称或任务说明；
- 父子关系；
- queued、running、waiting、completed、failed、cancelled、interrupted 状态；
- 开始时间与运行时长；
- 当前活动摘要；
- 流式输出或最终结果；
- 工具调用和错误；
- 实际工作目录；
- provider、模型和 thinking level；
- token 和费用；
- 是否阻塞主任务完成。

### 10.2 用户控制

用户可以：

- 查看子 Agent 详情；
- 单独中止仍在运行的子 Agent。

用户不能直接向子 Agent发送消息。单独中止后，主 Agent继续还是失败由 pi 运行语义决定，并在界面明确展示。

中止整个主任务时，必须级联取消所有仍在运行的子 Agent。

### 10.3 子 Agent 模型

主 Agent可以按子任务选择子 Agent的 provider、模型和 thinking level，但：

- 只能使用已认证且允许的模型；
- UI 必须显示实际选择；
- 模型不可用时不得静默替换；
- 用户不能在子 Agent运行中直接换模型；
- 主任务结果必须能追踪参与的子 Agent及其模型。

## 11. 会话、消息和队列

### 11.1 会话能力

用户可以：

- 查看项目中的会话与顶层任务；
- 创建新会话；
- 恢复和切换会话；
- 从有效分支点 fork；
- 重命名会话。

切换当前查看会话不得中止其他会话中的任务。

### 11.2 Prompt 接受

发送消息时应用应尽快返回“已接受”或具体的 preflight 拒绝，不得让 IPC 请求等待整个 Agent 运行结束。

preflight 至少验证：

- 任务和 runtime 可用；
- 输入有效；
- provider 已认证；
- 模型和 thinking level 可用；
- 附件仍有效；
- 项目资源和工作目录归属一致。

preflight 失败时保留草稿和尚未消费的附件。

### 11.3 运行中的新消息

主 Agent运行时，同一会话的新消息默认作为 follow-up：

- Composer 显示“将在当前运行结束后发送”；
- 用户可以显式切换为 steer，立即影响当前运行；
- steer 和 follow-up 使用不同文案、图标和状态；
- follow-up 按权威顺序显示；
- 用户可以清空尚未执行的 follow-up。

### 11.4 中止与队列

中止当前主 Agent运行时：

- 级联取消仍在运行的子 Agent；
- 保留部分回答、工具记录和文件修改；
- 未执行 follow-up 保留但进入暂停状态；
- 不自动运行下一条 follow-up；
- 用户可以继续队列、重新编辑发送或清空队列。

## 12. 模型、thinking 与认证

### 12.1 按消息选择

provider、模型和 thinking level 按消息选择：

- Composer 显示下一条消息的实际配置；
- 用户可在发送 prompt、steer 或 follow-up 前修改；
- 消息被接受时配置形成不可变快照；
- 修改 Composer 只影响之后发送的消息；
- 不改变正在运行的 Agent、已排队消息或其他任务；
- 每条运行记录可查看实际使用的配置。

恢复旧会话时，Composer 默认沿用最近一次成功发送的配置，但用户可以修改。

当前 pi SDK 的模型和 thinking level 主要是 session 级状态，原生 steer/follow-up 队列也不携带独立模型快照。实现前必须验证并明确以下映射：普通 prompt 可在开始新一轮前设置消息快照；steer 默认继承正在运行的主 Agent 配置，不得中途切换当前 run；需要独立模型快照的 follow-up 由 Desktop 在真正开始下一轮前设置对应配置，而不能提前交给无法保存该快照的上游队列。若继续使用上游队列，则应收窄相应产品承诺或推动上游公共 API 支持。

### 12.2 认证

用户可以查看 provider 认证状态、提交 API key、发起 OAuth 和 logout。必须满足：

- 保存的 API key 和 OAuth token 不回传 Renderer；
- 用户输入的 API key 通过一次性专用命令提交；
- 成功或失败后都立即清空前端秘密输入；
- OAuth 支持取消和超时；
- 凭据同步部分失败时重新查询状态，不引导用户盲目重复提交；
- 多任务可同时使用不同的已认证 provider。

## 13. Conversation 与工具呈现

### 13.1 消息

Conversation 必须展示：

- 完成消息；
- Markdown；
- 代码块；
- diff；
- thinking；
- 流式文本和 thinking；
- retry、compaction 和错误状态。

增量必须关联正确内容块，最终完成消息必须原子替换临时状态，不能产生重复时间线。

### 13.2 工具

每个工具调用至少显示：

- 工具名称；
- 开始状态；
- 参数摘要；
- 累计 partial result；
- 完成、失败或取消；
- 所属顶层任务和子 Agent；
- 必要的耗时信息。

长命令、长路径和无换行输出不得破坏布局。

## 14. Extension UI

首版完整支持：

- `select`；
- `confirm`；
- `input`；
- `editor`；
- `notify`。

每个请求必须标明来源项目、顶层任务和子 Agent。后台任务发出阻塞型请求时：

- 任务进入 waiting；
- 项目树显示持久标记；
- 默认发送适用的桌面通知；
- 用户可以跳转到请求来源；
- 请求不能因当前未查看该任务而丢失。

同一任务的多个阻塞请求按确定顺序处理。用户取消、单 Agent 中止、主任务中止、runtime 崩溃、应用退出或请求超时时，必须解决相关 pending request。迟到响应不得发送给失效 runtime。

Extension 文本按不可信内容安全渲染，不执行 HTML 或脚本；用户输入不进入普通持久化。

## 15. 通用文件附件

### 15.1 支持范围

首版支持受控通用文件附件，包括常见：

- 图片；
- 文本和日志；
- 源代码；
- 结构化数据；
- 文档；
- 压缩包。

具体 MIME、扩展名、单文件大小、数量和总大小在实现规格中确定，但必须形成明确 allowlist 和限制。产品入口可以接受通用文件选择，但只有存在明确、安全转换语义的类型才能发送：图片映射为上游支持的图片内容；文本类按大小和编码限制转换为当前消息文本内容；PDF、办公文档、压缩包及其他二进制类型在解析/引用方案完成安全评审前应明确拒绝，而不能只上传 metadata 或假装模型可读取。

### 15.2 选择与校验

附件只能通过系统文件选择器或明确批准的拖放、粘贴操作加入。Renderer 只持有 metadata 和短生命周期 token。

Main 必须重新校验：

- 文件类型；
- 大小；
- 可读性；
- 普通文件属性；
- 选择后是否变化；
- provider/model 是否支持。

不得自动解压并执行压缩包内容。目录、设备文件、特殊文件和明显的凭据文件必须拒绝或要求额外保护。

### 15.3 消息级生命周期

外部附件只作为当前消息输入：

- 不复制到任务 worktree；
- 不成为后续消息默认可访问文件；
- 不进入代码 diff；
- token 绑定任务和消息，不得跨任务复用；
- preflight 失败时保留以便重试；
- 消息被接受后消费授权；
- 后台失败后重试时需要重新确认附件；
- pi-desktop 不长期复制原文件内容。

## 16. 任务状态模型

每个顶层任务分别维护三个用户可见维度。

### 16.1 Agent 执行状态

- queued：等待并发槽位；
- running：主 Agent或子 Agent正在执行；
- waiting：等待用户或 extension 输入；
- completed：Agent 已结束；
- failed：运行失败；
- cancelled：用户中止；
- interrupted：因应用退出或异常中断。

### 16.2 验证状态

- not-run：未运行；
- running：验证中；
- passed：通过；
- failed：失败；
- partial：部分通过；
- unknown：无法判断。

测试未运行时不得显示“全部成功”。测试失败不自动丢弃变更，测试通过也不自动应用。

每条验证记录必须包含命令或验证类型、cwd、退出状态、起止时间、来源和关联的 `resultRevision`。文件状态在验证后变化时，旧验证结果不得继续代表当前成果，验证状态回到 not-run 或 unknown。Agent 的文字陈述不能单独构成 passed；只有可核验的工具执行或用户明确导入的结果才能形成验证记录。

### 16.3 成果状态

- no-changes：无文件变更；
- review-required：待审查；
- applicable：可应用；
- blocked：应用受阻；
- applied：已应用；
- discarded：已丢弃。

Agent 返回最终回答只表示执行结束，不等于验证通过或成果已应用。

## 17. 变更审查与应用

### 17.1 审查内容

任务完成、失败、中止或中断后，只要 worktree 有变更，用户都可以查看：

- 变更文件列表；
- 新增、修改、删除和重命名状态；
- 每个文件的完整 diff；
- Agent 执行状态；
- 验证状态和可验证的测试记录；
- worktree 路径；
- base commit；
- 目标工作区与目标分支；
- 是否存在未提交修改或任务内提交。

### 17.2 应用粒度

首版只能整项应用任务的全部变更：

- 可以逐文件查看；
- 不支持按文件勾选；
- 不支持按 hunk 选择；
- 应用前再次显示目标、文件数和变更摘要。

### 17.3 应用前提

应用前必须重新验证：

- 目标工作区存在；
- 目标工作区仍对应预期仓库；
- 目标工作区干净；
- base 与目标状态允许安全应用；
- 任务 worktree 完整；
- 已审查的成果版本没有在审查后发生变化；
- 全部变更通过预应用检查，并能够按首版支持的变更类型安全写入。

任务成果定义为 `base commit → 当前 worktree 文件状态`，而不是只读取未提交 diff。进入审查时记录 `resultRevision`；worktree、目标 ref 或文件状态随后变化时，既有审查和可应用状态立即失效，用户必须刷新后重新审查。实现规格必须定义支持的重命名、二进制、文件模式、符号链接、submodule、Git LFS 和稀疏检出边界，以及应用 journal 和进程异常后的恢复办法。在这些算法得到验证前，不得把跨文件写入宣传为绝对原子。

### 17.4 冲突策略

如果目标工作区有未提交改动，或变更无法干净应用：

- 停止应用；
- 不覆盖目标文件；
- 不留下半应用状态或冲突标记；
- 保留完整任务 worktree；
- 显示阻塞原因和恢复步骤；
- 用户处理目标工作区后可以重试。

首版不提供内置冲突解决器。

### 17.5 应用结果

应用成功后：

- 全部任务变更作为未提交修改进入目标工作区；
- 不自动提交；
- 不自动合并分支；
- 不更改作者或提交信息；
- 展示实际写入摘要；
- worktree 暂时保留，直到用户确认清理。

### 17.6 丢弃

用户可以永久丢弃未应用成果：

- 运行中任务必须先中止并完成清理；
- 显示项目、任务、worktree 路径和变更摘要；
- 明确说明不可恢复；
- 要求二次确认；
- 确认后删除 worktree 和其中未应用变更；
- 删除失败时保留现状并提供恢复信息；
- 已应用到目标工作区的修改不受影响。

## 18. 用量与费用

首版提供透明展示，但不实施硬预算：

- 每个顶层任务显示输入、输出和可用的缓存 token 数据；
- 每个子 Agent单独显示并汇总到顶层任务；
- 项目节点聚合当前应用运行期间的任务用量；
- 全局区域显示本次应用运行期间累计用量；
- 按实际消息和模型分别计算；
- 标明费用是 provider 实际返回还是估算；
- 无法确定价格时显示“费用未知”，不得显示虚假的零；
- 中止任务不清除已产生用量。

首版不因达到 token 或费用阈值自动暂停任务。

## 19. 桌面通知

首版使用 Linux 桌面通知：

- 后台任务等待用户输入时默认通知；
- 后台任务失败时默认通知；
- 普通完成通知默认关闭，可在设置中开启；
- 当前可见任务不重复发送系统通知；
- 点击通知聚焦已有主窗口并跳转到对应项目、任务或请求；
- 相同状态去重，避免通知风暴；
- 通知内容脱敏，不包含完整 prompt、文件内容、工具输出、凭据或敏感完整路径；
- 系统通知不可用时，项目树标记仍必须完整。

## 20. 退出、重启与恢复

### 20.1 关闭窗口

“后台运行”只表示在应用内切换任务后继续运行，不表示关闭应用后继续。

存在运行任务时关闭主窗口：

- 显示确认对话框；
- 展示运行中的顶层任务和子 Agent数量；
- 取消关闭时所有任务保持原状；
- 确认退出时中止全部主任务并级联取消子 Agent；
- 取消 trust、extension 和其他待响应请求；
- 保留 session、任务记录、follow-up 队列和未应用 worktree；
- 有界清理后退出，局部清理失败不得无限阻塞；
- 首版不驻留托盘。

### 20.2 重启恢复

重新启动后恢复：

- 项目记录；
- 顶层任务和会话；
- worktree 路径和 base commit；
- 消息、工具和子 Agent历史；
- follow-up 队列内容、顺序、消息级模型快照和暂停状态；
- 变更和审查状态。

恢复 follow-up 队列需要持久化尚未执行的用户消息。该内容只能保存在 Main 控制、权限受限的专用任务状态存储中，不得进入 Renderer storage、普通日志、系统通知或诊断摘要；消息执行、用户清空队列或任务永久删除后应及时删除。若实现阶段无法满足受控持久化，必须收窄为重启后不恢复消息内容，不能只恢复一个无法继续的队列占位。

退出前处于 running、queued、waiting 或 aborting 的任务统一标记为 interrupted。应用不得自动继续模型请求、命令或子 Agent。

### 20.3 手动继续

用户可以恢复原会话，在原 worktree 中发送新的继续指令：

- 保留历史消息和文件修改；
- 不假装从中断命令的机器执行点恢复；
- 旧工具和子 Agent标记为 interrupted；
- 用户点击继续前可补充或修改说明；
- 新一轮重新检查文件、Git 状态、模型和项目资源决定；
- 恢复受并发上限约束；
- session 无法恢复时仍保留 worktree，并允许审查、应用或丢弃。

恢复时必须验证目录和 Git 事实，不能只信任缓存。worktree 丢失、损坏或被外部删除时进入可诊断错误状态。

## 21. 错误、失步与恢复

### 21.1 错误要求

所有用户可见错误必须说明：

- 哪个操作失败；
- 用户当前数据和任务是否安全；
- 是否可恢复；
- 建议的下一步；
- 必要时的 `diagnosticId`。

不得向 Renderer 返回原始 `Error`、stack、凭据、完整 prompt、环境变量或敏感完整路径。

### 21.2 事件一致性

多任务事件必须关联明确的项目、顶层任务、Agent 和 runtime 身份。Renderer：

- 不得把一个任务的事件应用到另一个任务；
- 必须丢弃失效 runtime 的迟到事件；
- 检测到事件缺口时停止猜测并重新请求该任务或全局一致性 snapshot；
- 重同步失败时提供手动重试；
- 不得因当前任务切换而丢失后台任务事件。

### 21.3 Runtime 崩溃

可被宿主捕获且不终止 Electron main 的单个 runtime 异常发生时：

- 停止相关运行指示；
- 标记未完成消息、工具和子 Agent；
- 结束或失效相关 extension 请求；
- 保留完成消息和 worktree 修改；
- 显示脱敏错误和诊断 ID；
- 提供恢复原会话、审查成果或重新创建任务的入口。

如果 pi SDK、extension 或 native dependency 与 Electron main 同进程运行，`process.exit()`、event-loop 阻塞、OOM 或 native crash 可能同时终止整个应用和全部任务，无法保证显示上述实时崩溃界面。首版必须在架构修订时决定是否用 utility/child process 提供故障隔离；若仍同进程，产品承诺应限定为“重启后从持久状态恢复并标记 interrupted”，并明确一个 runtime 可能影响所有任务。独立进程提供故障隔离，不等于权限沙箱。

## 22. 安全与隐私

### 22.1 权限边界

pi 以启动用户权限运行。项目资源信任不是系统沙箱。Renderer 不得直接获得：

- Node.js API；
- Electron 原始 IPC；
- shell；
- 任意文件读写；
- pi SDK 实例；
- provider 凭据。

所有宿主命令必须是固定 allowlist，并在 Main 中对 `unknown` 输入执行 schema 校验。

### 22.2 不可信内容

以下全部按不可信数据处理：

- Markdown 和 HTML；
- 模型输出；
- 工具和终端输出；
- diff；
- 文件路径和链接；
- extension 文本；
- 附件 metadata。

禁止任意脚本执行、远程应用代码和未批准导航。拒绝 `javascript:` 及任意外部 `file:` 导航。批准的外链交给系统浏览器。

### 22.3 凭据

- 已保存 API key 和 OAuth token 不回传 Renderer；
- 不在 Electron `userData` 中复制 pi 凭据；
- 凭据不进入普通日志、系统通知、错误报告或遥测；
- Renderer 不持久化用户新输入的秘密。

### 22.4 日志和持久化

普通日志不得记录：

- 完整 prompt；
- 文件或附件内容；
- 环境变量；
- API key 或 token；
- 认证文件；
- 完整 IPC payload；
- 敏感完整路径。

pi-desktop 只持久化完成产品恢复所需的任务 metadata、受控的未执行 follow-up 内容、窗口状态和应用偏好。任务记录至少包含稳定的 `taskId`、`projectId`、pi session 引用、worktree 身份与路径、base commit、目标工作区、预期目标 ref、`resultRevision` 和生命周期状态；同一个 pi session 同一时间不得绑定到两个活动顶层任务。未执行消息属于用户内容而非普通 metadata，必须保存在 Main 控制、权限受限的专用存储中，并具有明确的删除生命周期；不得进入 Renderer storage、普通日志、通知或诊断摘要。pi 管理的 session、认证、模型设置和 trust store 继续由 pi 公共 API 管理。

上述约束只覆盖 pi-desktop 自身控制的 Renderer 持久化、应用日志、诊断、通知和错误响应。provider、用户或项目 extension、工具以及它们启动的进程可能按各自行为处理输入；项目资源决定和 pi-desktop 日志策略不能约束这些高权限代码。

## 23. 无障碍、键盘与布局

- 所有关键流程可仅用键盘完成；
- 所有交互控件具有可见焦点；
- 图标按钮提供 tooltip 和 accessible name；
- 对话框打开时聚焦合理元素，关闭后恢复触发位置；
- 状态变化不能只依赖颜色；
- 屏幕阅读器可以理解 running、queued、waiting、aborting、failed、interrupted 和 review-required；
- 窄窗口下项目树、中央会话和详情抽屉仍可访问；
- 长项目名、模型名、路径、命令和输出不得覆盖相邻控件；
- 高频流式更新不得导致 Composer、导航或任务详情不可控跳动。

## 24. 设置

首版设置至少包括：

- 顶层任务并发上限；
- 每任务子 Agent并发上限；
- 全局 Agent总上限；
- 新会话默认 provider、模型和 thinking level；
- 等待输入通知开关；
- 失败通知开关；
- 完成通知开关；
- 主题和非敏感界面偏好；
- 项目资源决定的查看与更改入口。

设置变更不得泄漏凭据，也不得静默改变已经接受的消息和正在运行的 Agent。

## 25. 关键验收场景

### AC-01 跨项目并行

1. 打开项目 A 和项目 B；
2. 分别启动一个任务；
3. 两个任务同时运行；
4. 在两者间切换；
5. 未显示任务继续接收事件并最终完成。

### AC-02 同项目 worktree 隔离

1. 在一个 Git 项目中创建两个任务；
2. 两个任务基于创建时显示的 `HEAD` 建立不同 worktree；
3. 两个任务可以并行修改同名文件；
4. 原始工作区在应用前保持不变；
5. 每个任务只显示自己的变更。

### AC-03 非 Git 并行被阻止

1. 在非 Git 目录启动一个任务；
2. 尝试启动同项目第二个任务；
3. 应用拒绝并说明缺少安全隔离方式；
4. 不创建副本，不共享目录并行。

### AC-04 子 Agent 观察与中止

1. 主 Agent启动多个子 Agent；
2. 详情面板显示树、状态、模型、输出和工具；
3. 用户单独中止一个子 Agent；
4. 其他子 Agent不被错误中止；
5. 中止整个主任务时全部剩余子 Agent被取消。

### AC-05 并发调度

1. 使用默认 3/3/6 上限启动超过容量的 Agent；
2. 超额项显示等待并发槽位；
3. 槽位释放后按调度顺序启动；
4. 不与 follow-up 或 retry 状态混淆。

### AC-06 项目资源不加载

1. 打开包含受保护 pi 资源的项目；
2. 选择“不加载项目资源”；
3. 项目仍可创建任务；
4. 受保护资源不加载；
5. UI 持续显示状态及非沙箱说明；
6. 重启后持久决定仍生效。

### AC-07 Follow-up 与中止

1. 主 Agent运行时发送新消息；
2. 默认进入 follow-up；
3. 用户可改为 steer；
4. 中止主 Agent后 follow-up 保留且暂停；
5. 用户可以继续或清空。

### AC-08 Extension 后台请求

1. 后台任务发出 `confirm` 或 `editor` 请求；
2. 项目树显示等待输入；
3. 系统通知跳转到正确任务；
4. 响应只提交给来源 Agent；
5. Agent 中止后迟到响应被拒绝。

### AC-09 完整 diff 应用

1. 任务产生多文件变更；
2. 用户逐文件查看完整 diff；
3. 目标工作区干净；
4. 用户点击整项应用；
5. 全部变更作为未提交修改出现；
6. 应用不创建提交。

### AC-10 脏工作区与冲突

1. 目标工作区存在未提交修改，或目标状态与任务成果冲突；
2. 应用操作安全停止；
3. 目标工作区不出现半应用状态；
4. worktree 和成果完整保留；
5. 用户处理后可重试。

### AC-11 退出和恢复

1. 存在运行任务、子 Agent、follow-up 和未应用成果；
2. 关闭窗口时显示确认；
3. 确认后中止并退出；
4. 重启后任务标记 interrupted；
5. worktree、历史和队列恢复；
6. 用户手动继续原会话；
7. 不自动发起模型请求。

### AC-12 凭据与附件安全

1. 提交 API key 和通用文件附件；
2. Renderer 不得到已保存 key 或任意文件读取能力；
3. 附件只用于目标消息且不写入 worktree；
4. 日志、通知和错误不包含秘密或文件内容；
5. token 不能跨任务重放。

### AC-13 多任务事件隔离与失步恢复

1. 两个任务产生相同 tool call ID 和高频流式事件；
2. 其中一个 runtime 重建且旧事件迟到；
3. 重复、乱序或缺失事件触发按任务重新同步；
4. 只有正确任务被更新；
5. 一个任务重新同步不冻结其他任务。

### AC-14 信任决定与多个 worktree

1. 分别验证“加载并记住”“仅本次加载”和“不加载项目资源”；
2. 同一项目多个 worktree 使用相同项目级决定；
3. 内部 worktree 路径不产生独立持久信任记录；
4. 重启后“仅本次加载”失效，持久决定保留；
5. 项目资源决定改变后只影响新建或重建 runtime。

### AC-15 调度防死锁

1. 多个主 Agent同时请求并等待子 Agent；
2. 等待父 Agent释放执行槽；
3. 依赖的子 Agent获得调度机会；
4. queued Agent可以取消；
5. 动态降低上限不会中止运行中 Agent，也不会导致永久饥饿。

### AC-16 成果版本与外部 Git 变化

1. 用户完成 diff 审查；
2. 随后 worktree、目标分支或目标工作区状态发生变化；
3. 原审查与 applicable 状态失效；
4. 应用被阻止并要求刷新；
5. 重新审查新的 `resultRevision` 后才能应用。

### AC-17 应用异常恢复

1. 对支持的新增、修改、删除、重命名、二进制或模式变化执行预应用检查；
2. 在应用不同阶段模拟进程退出、磁盘错误和权限错误；
3. 重启后通过 journal 识别状态；
4. 不把未知或半完成状态显示为 applied；
5. 用户获得明确恢复或手动处理指引，worktree 保留。

### AC-18 恢复失败降级

1. 分别模拟 session 丢失、worktree 丢失、Git 损坏和任务 metadata 局部损坏；
2. 应用不创建空任务冒充恢复；
3. 可用的会话、worktree 或 diff 数据继续保留；
4. 用户可审查、应用、丢弃或获得手动恢复路径；
5. 错误包含脱敏诊断 ID。

### AC-19 安全渲染和外链

1. 消息、diff、工具输出和 extension 文本包含恶意 HTML、ANSI、超长无换行文本及编码混淆链接；
2. 不执行脚本或任意导航；
3. `javascript:` 和未批准的 `file:` 被拒绝；
4. 外链只按允许协议交给系统浏览器；
5. 窄窗口和键盘焦点仍可用。

### AC-20 有界退出

1. runtime、子 Agent或 extension 请求不响应取消；
2. 退出清理达到超时后应用仍能结束；
3. 下次启动将相关任务标为 interrupted；
4. session、follow-up 和 worktree 成果未被静默丢弃。

## 26. 架构修订结果

2026-09-18 创建的 [`architecture/electron-architecture.md`](architecture/electron-architecture.md) 已将以下差异纳入新的 Proposed 系统架构；旧单 runtime 提案已移至 [`archive/electron-architecture.md`](archive/electron-architecture.md)。这些条目仍用于核对模块细化和实现是否完整：

1. **单活动 runtime**改为多个并行顶层 runtime/task；
2. `RuntimeController` 不能再只拥有唯一 runtime，需要任务/runtime registry 或等价所有权模型；
3. 全局单一 `runtimeGeneration` 不足以路由多任务事件，需要稳定的项目、任务、Agent 和 runtime 身份；
4. “切换项目或 session 等于 replacement”改为“切换当前视图不影响后台 runtime”；
5. Renderer 不能只维护一份当前 conversation 投影，需要任务摘要集合和按任务隔离的详细状态；
6. snapshot/event 初始化、失步恢复和 sequence 需要支持多任务；
7. application lifecycle 需要统一管理多个 runtime、worktree 和 pending request；
8. 附件从图片扩展为受控通用文件；
9. 增加 worktree 管理、任务成果审查、整项应用和丢弃能力；
10. 增加子 Agent 详细可观察性、单独中止和多级并发调度；
11. 模型配置从单一当前模型扩展为每条消息的不可变运行快照；
12. 单窗口假设仍保留，但单活动工作区和单活动会话假设不再成立。

新系统架构已经为以下资源指定逻辑 owner；多任务模块设计文档尚未编写，实现前应在 `docs/modules/` 下按该 owner 模型补齐：

- project/task/runtime registry；
- 顶层与子 Agent scheduler 及并发槽位；
- 每个 runtime incarnation 的 generation 与事件 sequence；
- 全局任务摘要 snapshot 和按任务详细 snapshot；
- task/session/worktree 持久化与恢复；
- worktree 创建、验证、锁定和清理；
- Git 状态、diff、`resultRevision` 和 validation record；
- apply/discard 事务及恢复 journal；
- desktop notification；
- subagent orchestration；
- 绑定 `taskId + runtimeId` 的 attachment、trust、extension 和 request scope。

这些所有权问题已在系统架构层获得唯一答案；在模块索引和单模块文档完成多任务修订前，仍不应按现有单 runtime 模块文档开始实现。
